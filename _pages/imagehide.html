Where this runs. All encoding and decoding executes inside your browser via ONNX Runtime Web. Your image is never uploaded — the model is fetched once from a CDN and runs entirely on-device, in a Web Worker. No server is involved in the inference path.

Speed in production. The timings above are browser inference — single-threaded WASM on mobile, WebGPU on desktop — which is the slowest path the same model would ever run on. The encoder is only 251 K parameters and is designed to run on-camera at capture time. On real production hardware the speedup is dramatic:

  • Phone NPU (Apple ANE / Snapdragon Hexagon, the actual deployment target): < 50 ms per 0.5 MP image — roughly 100–500× faster than the browser-WASM mobile timing you see here.
  • Server CPU, native ONNX Runtime with AVX-512 + multi-threading: 50–200 ms.
  • Server GPU, native ONNX Runtime with fp16: 5–20 ms.

The demo gives up most of that headroom on purpose: it's single-threaded (browser WASM can't use threads without server-side COOP/COEP headers, which GitHub Pages doesn't serve), fp32 decoder + fp16 encoder (full fp16 conversion of the decoder fights the converter), one image at a time instead of batched, and pays a JS↔WASM marshaling cost on every tensor crossing.

Why your image got downsampled. Browsers cap per-tab memory tightly (≈ 300 MB on iOS Safari, a few GB on desktop). The decoder allocates ≈ 12 MB of float32 tensor per megapixel, plus intermediate buffers; running 11 attacks on a 12 MP phone photo overruns Safari and crashes the tab. To stay inside that envelope the demo auto-resizes any input above 1 MP on mobile or 2 MP on desktop, preserving aspect ratio. A typical 12 MP phone photo becomes ~1224×816 (desktop) or ~866×577 (mobile). The model itself has no such limit — on a phone NPU or server it runs the full 12 MP without resizing.
